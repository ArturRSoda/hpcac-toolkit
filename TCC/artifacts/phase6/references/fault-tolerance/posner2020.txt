System-Level vs. Application-Level Checkpointing
Jonas Posner
University of Kassel, PLM, Kassel, Germany
jonas.posner@uni-kassel.de
I. INTRODUCTION
Fault tolerance is becoming increasingly important since
the probability of permanent hardware failures increases with
machine size. A typical resilience approach to fail/stop failures
today is checkpointing, which can be performed on system- or
application-level. Both levels come in many variants, but they
fundamentally differ. On system-level, no code changes are
required, full program states are saved, and after a failure the
program must be restarted from the last checkpoint. In con-
trast, on application-level, only user-deﬁned data are check-
pointed, which requires some programming effort. Thereby,
the running time overhead may be reduced signiﬁcantly, and
programs may continue execution after failures.
Typical
representatives
include
DMTCP
(Distributed
MultiThreaded
Checkpointing)
[1]
for
system-level,
and
FTGLB (Fault Tolerant Global Load Balancing) [2] for
application-level. DMTCP is a user-space library, which
checkpoints parallel programs transparently and restarts them
from a checkpoint. DMTCP supports many programming
languages and HPC environments.
FTGLB bases on a distributed task-pool pattern, and writes
uncoordinated in-memory checkpoints. Checkpoints only in-
clude task descriptors and interim results, and are written at
regular time intervals and at certain events, e.g. work stealing.
In this work, we experimentally compare DMTCP and
FTGLB with up to 320 processes. Moreover, we derive for-
mulas for predicting running times, including failure handling.
With these formulas, we compare DMTCP and FTGLB in
failure-prone and larger settings. Overall, the results clearly
show that the application-level optimizations of FTGLB are
worthwhile since the running time overhead is signiﬁcantly
lower than that of DMTCP.
II. EXPERIMENTS
The experiments were run on Goethe-HLR1, which provides
Inﬁniband-connected nodes with two 20-core Intel Xeon Sky-
lake Gold 6148 CPUs and 192 GB of main memory. We started
40 workers per node, each worker being a system process.
We used DMTCP in its latest version 3.0 (Mar. 7, 2020)2,
FTGLB and its non-resilient base GLB in their latest revisions
(Dec. 15, 2019)3, and Java in version 1.8.0 221.

(FT)GLB implements a model of dynamic independent
tasks (combined with a resiliency scheme) as a framework [2].
Therefore, users do not need additional programming effort for
load balancing and resiliency. As benchmark, we deployed
our own synthetic one (called SynBench), which calculates
π using the Monte Carlo method. Its main purpose is to
provide smooth weak scaling to enable an accurate timing
analysis of both checkpointing systems. However, obtained
experimental results could be translated to other applications,
under consideration of characteristics like number of tasks,
stealing rate, result type, and task descriptor size.
SynBench deploys a ﬁxed number of static tasks which are
initially distributed evenly over all workers. We conﬁgured a
base calculation time T B = 100s, 6000 tasks per worker, and
20% task duration ﬂuctuation. The latter enforces an initial
work imbalance between workers despite the same number
of tasks per worker. A failure-free and unprotected execution
takes T B plus some time for work stealing. For FTGLB, we
set the regular checkpoint interval to 10s, see [2].

B. Failure Handling
Failures are handled differently: FTGLB supports shrinking
recovery, whereby a program continues execution with fewer
workers. For that, a recovery procedure is performed causing a
negligible overhead [2]. In contrast, a DMTCP program aborts,
but can be restarted from the last checkpoint. Figure 2 presents
DMTCP restart timings. It can be observed, that the restart
costs increase with the number of workers. The increase is
stronger for scratch than for shm. Again, the limited bandwidth
of the distributed ﬁle system is a dominating factor.

calculated a failure-free and unprotected baseline, as twice the

The results clearly show that FTGLB works more efﬁciently
than DMTCP. Especially for large computations, the effort of
application-level (avoiding distributed ﬁle system and restart)
pays off. Future work may consider other checkpointing
systems, and more clusters for experiments.
